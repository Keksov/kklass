# Оптимизация kklass — что было сделано (2026-09-05)

Этот файл раньше описывал прототип «shared dispatch» (`experimental/kklass_new.sh`)
как рекомендацию на будущее. Рекомендация реализована в основном `kklass.sh`
фазами P4a/P4b плана `PLAN.md`; ниже — фактическая архитектура и цифры.
Подробный журнал (находки, решения, гейты) — `kklass_ledger.json`.

## Что было

Каждый инстанс получал при `.new` полную копию всей машинерии диспетчеризации
(`_invoke`, `_exec`, `_run_frame_body`, `_find_method`, `.call`, `.parent`,
аксессоры) — ~7–8 КБ eval'нутых функций на объект, 24 функции на инстанс при
10 методах. Два пути форкали subshell и стоили по 16 мс уже при 50 объектах,
потому что fork копирует весь шелл: `.delete` (`unset -f $(compgen ...)`) и
чтение вычисляемого свойства (`RESULT="$($this.call getter)"`).

## Что стало

**Рантайм один на шелл.** Диспетчеризация живёт во фреймворке:
`kk._run_frame_body`, `kk._invoke`, `kk._exec`, `kk._find_method`, `kk._call`,
`kk._parent`, `kk._constructor_exec`, `kk._delete`, `kk._property`,
`kk._prop_plain`, `kk._prop_computed`, `kk._prop_lazy`. Первый аргумент везде —
имя инстанса.

**Инстанс — это данные плюс однострочные обёртки:**

```bash
declare -gA obj_data
obj_class="Person"
obj.property() { kk._property obj "$@"; }
obj.name()     { kk._prop_plain obj Person name "$@"; }
obj.greet()    { kk._exec obj greet Person "$@"; }      # Person = класс, ОПРЕДЕЛИВШИЙ метод
obj.call()     { kk._call obj "$@"; }
obj.parent()   { kk._parent obj "$@"; }                 # только если есть родитель
obj.delete()   { kk._delete obj "$@"; }
```

Namerefs свойств (`local -n name="obj_data[name]"`) строятся при вызове из
таблиц класса инстанса, поэтому генерируемого кода диспетчеризации нет ни на
инстанс, ни на класс. Семантика не изменилась: фреймы, `inherited`/`.parent` по
классу-владельцу, виртуальный `.call`, `kk._return`, видимость, `REPLY` у
stateful-статиков.

**Горячий путь урезан (P4b):**

- флаг `<Class>_has_nonpublic` выставляется в `endImplementation`; если все
  члены публичные, проверка видимости не вызывается вовсе (раньше она начинала с
  `declare -p` таблицы — форматирование всей таблицы на каждый вызов);
- push/pop фрейма встроены в `kk._invoke` на массивах kkore `__KLIB_FRAME_*`
  (тот же код, что `kv.framePush/framePop`, минус шесть вызовов функций);
- `kk._return` проверяет `[[ -v ]]` вместо `declare -p`.

**Форки убраны:** `.delete` берёт список функций из таблиц класса;
`function`-геттер вычисляемого свойства выполняется в текущем шелле.

## Цифры (bash 5.2.37, класс с 3 свойствами и 10 методами, `bench/kklass_bench.sh`)

| метрика | до | после |
|---|---|---|
| шаблон инстанса | 6970 байт | 1110 байт |
| функций на инстанс | 24 | 19 (= члены + 4) |
| `.new` | 904 мкс | 188 мкс |
| вызов метода | 383 мкс | 206 мкс |
| чтение свойства | 117 мкс | 41 мкс |
| запись свойства | 120 мкс | 27 мкс |
| `.delete` при 1000 объектах | 1.8 с | 0.19 мс |
| чтение вычисляемого свойства при 50 / 1000 объектах | 16 / 39 мс | 0.65 / 0.63 мс |

На bash 5.3.9 цифры на 10–20 % лучше, картина та же.

## Правила, вынесенные из бенчмарков

- **Не форкать в горячих путях.** Fork копирует весь шелл; при тысячах функций
  это десятки миллисекунд за вызов.
- **Не перечислять таблицу функций большого шелла** (`compgen -A function`,
  с fork'ом или без): на cygwin/msys после такого перечисления каждый
  последующий вызов функции становится ~1.7× медленнее до конца жизни
  процесса. Бенчмарк считает функции, пока шелл маленький, и выводит большое
  число арифметически.
- **Два bash.** Всё проверяется на 5.2.37 (MSYS2) и 5.3.9 (cygwin,
  `C:/bin/msys64/usr/bin/bash.exe`, с cygwin-`bin` первым в PATH).

## experimental/

`kklass_new.sh`, `kklass_cnfh.sh`, `kklass_new_fields.sh` и их тесты — история:
прототип, идея которого (методы один раз, объект = данные + тонкие прокси)
теперь и есть основная реализация. В загрузке и тестах не участвуют; папку
можно удалить отдельным коммитом.
